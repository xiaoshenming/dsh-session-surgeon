# Changelog

All notable user-facing changes to dsh-session-surgeon. Dates are UTC.

## Unreleased

> The rolling `#main` install reports **0.2.6** from 2026-10-08; this section is what that install carries.

### Fixed

- **`compact` could not produce a loadable file, and crashed before it could try.** Found by pointing the tool at this machine's own store while answering [#8466](https://github.com/deepseek-ai/deepseek-harness/discussions/8466) — the flagged session there is exactly the "history too big" case `compact` exists for. Three independent defects, all measured against the released reader: (1) the CLI printed `formatRepairText(result)`, which reads `plan.actions.length` — a compact plan has no `actions`, so **every** `compact` run died with `Cannot read properties of undefined (reading 'length')` regardless of `--format`; (2) the written header carried `seedLength`, a v0/v1 field that the v4 header gate refuses as `unexpected field seedLength` and our own `isHeaderLine` forbids for `version >= 2`; (3) the slice renumbered `seq` but left `data.turn`/`data.step` at their old values, so the fold refused it with `turn/start does not open the expected turn`. Compact now drops the earlier turns, renumbers seqs from 0 and turns/steps from 1, and shifts every seq-valued reference that stays inside the slice by the cut — `surfaceOp`/`sourceEventSeqs` on the event, `shadowedSeqs`/`shadowedRange`/`headerSeq`/`messageSeqs`/`throughSeq`/`sourceEventSeq`/`protectedHead` inside `data` (that member list is measured over the whole local store, not assumed: `throughSeq` on delivery events and `sourceEventSeq` on `command/done` are only visible there). It refuses — writing nothing — when a reference points at a dropped event, when a turn/step pair cannot be mapped, or when the session has an inherited seed prefix (`isSeeded`, or a v0/v1 `seedLength > 0`), because dropping an inherited prefix has no defined meaning. Verified by compacting every v4 session in this machine's store at `keep-last-turns` 1, 2 and 3: **0 of the produced files fail** `assertReleasedV4Relationships`, `Session.fromRestore` or the embedded-stream comparison (7 accepted, 6 refused, 17 no-op). A test drives the released gates on a compacted slice, which is what caught (3) and the two missing reference members.
- **A lone surrogate is located, and the panel can say what it means** ([#8466](https://github.com/deepseek-ai/deepseek-harness/discussions/8466)). `lone-surrogate` was the one common verdict the panel had no copy for — the badge showed the raw code and the hint fell back to the generic default in all three locales, which is the same "the user sees no reason" the report is about. The message said only "isolated UTF-16 surrogate in payload"; it now names the row: `isolated UTF-16 surrogate in seq 25 (tool/result) — JSON.stringify escapes it and the provider rejects every later request body (HTTP 400, #8466); repair replaces it with U+FFFD`, and carries the seqs. Measured on a real 184-event v4 log poisoned the way the report describes (a `tool/result` text carrying U+DC3E): **both official read-time gates accept the file as written**, which is precisely why nothing warns the user, and after `repair` the escapes are gone, the seqs are unchanged and the gates still accept. The four other codes the panel had no label for are covered too (`torn-tail`, `foreign-version`, `header-parse-error`, `retired-fields`), and a test now asserts every code in `HEALTH_RANK` has copy in all three locales, so this cannot reopen silently.
- **A lone surrogate in the header is reported rather than left as a silent dead end.** `inspect` flagged the file while `repair` reported nothing to do, with no hint that the two were talking about different places. A header hit (reachable on Windows, where a directory name can carry an unpaired surrogate and the header records the `cwd`) is now named as such and says it is only reported: rewriting `cwd` would move the log out of the directory that names it, so the repair there is a directory rename, not a file edit.

### Docs

- **The shipped skill had the released producer-kind table one name short.** `RELEASED_SAME_NAME_PRODUCERS` holds **25** entries, not the 24 that `skills/dsh-session-surgeon-update/SKILL.md` and `docs/REPAIR-SPEC.md` both claimed — our miscount, which had already reached a public reply on [#6559](https://github.com/deepseek-ai/deepseek-harness/discussions/6559) and was corrected there. The table itself was never wrong: `src/message-shapes.mjs` copies the released block verbatim, and a test drives the released v3→v4 stage and compares the kind it derives for every mapped name and role. Both documents now also record two facts measured while answering [#9099](https://github.com/deepseek-ai/deepseek-harness/discussions/9099): the rewrite table runs **only** inside the v3→v4 migration (`rewriteV3MessageSource` has a single call site, in that stage's `transformRun`), so the read path — `assertReleasedV4Relationships` → `assertV4MessageSources` → `source()` — never rewrites, and the literal `plugin` kind is a hard refusal there while the `plugin:<name>` fallback is admitted; and the per-slot kind rules come from `dsh-session`'s `assertMessageEventShape`, not from `producerKind`'s role branch. No behaviour changed.

### Fixed

- **A message source the reader refuses is no longer reported as `ok`** (new health code `producer-source-invalid`). Format v4 admission runs `assertV4MessageSources` over every message slot on every read and refuses the whole log when `source` is not an object, or `kind` is absent, empty, not a string, or not the kind the slot demands. Our scanner only knew the retired `{kind:"plugin"}` literal, so a row with no `kind` at all — the shape reported in [#9099](https://github.com/deepseek-ai/deepseek-harness/discussions/9099) — read as healthy while the loader refused the file: a false negative, which is worse than a crash because nothing tells the user to look. The rules are measured against the reader shipped in the desktop's `0.2.0-rc.2` bundle rather than assumed, and they differ per slot: `user/message` and `developer/message` accept any non-empty kind except the `plugin` literal, `system/message` accepts only `system-prompt`, `assistant/message` only `model`, and `tool/result` only `tool`. Repair still writes nothing here: an absent or wrong kind has no unique successor inside the artifact, which is exactly why the `plugin` literal keeps its own repairable code and is not folded into this one. A test asserts the detector fires **exactly** when the released gates refuse — both `assertReleasedV4Relationships` and the seed constructor `Session.fromRestore` — across ten measured slot/variant cases, and the four sessions in this machine's store still read unchanged.

### Fixed

- **The agent tools work on a standard install again** ([#7](https://github.com/xiaoshenming/dsh-session-surgeon/pull/7), reported and started by @Error0422-bit). Three independent defects made `session_scan` / `session_inspect` / `session_repair` fail with `value is not lossless JSON` or a bare crash. The runtime probe only looked for `@deepseek-ai/dsh-session` next to the `dsh` launcher on `PATH`, so on an npm-global install — where the harness nests its runtime under `node_modules/@deepseek-ai/dsh/node_modules/` — resolution failed, the format version fell back to 0, and every v4 session was reported `foreign-version`. Report payloads carried `undefined` members (`error` on every healthy entry, `tornStart`, `overflowLastSeq`, `events`), which the harness's own `snapshotJsonValue` refuses *whole*, and an early decode return omitted the arrays `inspect` iterates, so a header-only verdict ended in `turnStep is not iterable`. Reproduced here on a machine with no `dsh` on `PATH`: `inspect` crashed exactly that way before the fix and reports normally after it. The probe now anchors on the harness package itself, absent members are omitted instead of carried, the early-return payload carries every array its callers read, and one `toLosslessJson` boundary normalizes whatever a tool returns.
- **The event catalog now comes from the install the runtime resolved.** The contributor's probe fixed `runtime.mjs`; `known-types.mjs` resolved the same package its own way and kept missing it, so `KNOWN_SESSION_EVENT_TYPES` silently stayed on the 48-type fallback while the runtime itself resolved — `model/selection` was missing from the vocabulary and a test that only runs once the runtime resolves failed. Both now go through one `resolveInstalledPackage()`, and the catalog loads (59 types here, from `lib/types/known-event-types.js`).
- **`toLosslessJson` no longer leaves array holes behind.** The boundary claimed a hole becomes `null`, but it used `Array.prototype.map`, which *skips* holes, so a sparse array came back still sparse and the harness refused it — verified against the harness's own `snapshotJsonValue`: `[1, , 3]` was refused before the fix and accepted after. A test pins each shape (hole, `-0`, `Infinity`, `NaN`, `undefined` member, cycle) to that predicate, so the boundary is measured rather than asserted.

### Fixed

- **The retired `{kind:"plugin", plugin}` message source is repaired, not just reported** ([#7772](https://github.com/deepseek-ai/deepseek-harness/discussions/7772), [#6559](https://github.com/deepseek-ai/deepseek-harness/discussions/6559)). Format v4 admission demands a producer-owned kind (`format v4 message requires a producer-owned source kind`), so a log that still carries the wrapper is refused whole on read. The earlier note here claimed the successor kind "cannot be invented offline" — measured against the released converter, that is wrong: the v3→v4 stage derives it with `producerKind(plugin, role)`, a *total* function (a rename table, a first-party same-name set, a role-sensitive `@deepseek-ai/dsh-system-prompt` case, and the `plugin:<name>` fallback), and that function plus `rewritePluginSource` are byte-identical in `0.1.7-rc.2` and in the `0.2.0-rc.2` the desktop bundles. The repair applies exactly that function: it replaces `kind`, drops `plugin`, and keeps every other member (so `automationId` / `runId` / `scheduledFor` survive, which is what the writer's own patch produced). A source whose `plugin` is not a string is left alone, because there the released converter throws. Table drift is guarded by a test that drives the released stage itself and compares the kind it emits for every mapped name and role, and by another that shows the released fold refusing the wrapper and accepting the repaired row.
- **`step-after-turn-end` no longer fires on a replacement `tool/result`.** Every released fold routes a `tool/result` whose `surfaceOp` is not the literal `"append"` through `requireTurn()` alone and returns before `requireStep`, so the row's own `turn`/`step` are never compared against the open pair: an idle prune pass that lands inside a *later* open turn is legal, and the only refusal left for those rows is "no turn is open at all" (which `prune-tail-outside-turn` owns). Found the same way as the dangling false positive — by pointing the tool at a real store: a live 3311-event session whose middle carries 21 such rows was reported as `step-after-turn-end` while the verifier shipped in the desktop's `0.2.0-rc.2` bundle accepts it. The detector now skips those rows; appends, `assistant/message` replacements and the rest still go through the turn/step comparison exactly as before.
- **`v4-literal-plugin-source` now sees `developer/message` and `system/message` too.** The official walker (`mapEventMessages`) hands those slots to the same converter, and our scan only covered `user/message`, `assistant/message`, `tool/result` and the two message arrays — so a wrapper in a developer or system message was invisible, which is also where the role-sensitive `system-prompt` rename lives.

### Fixed

- **`dangling-tool-call` no longer fires on an interrupted tail**, which is the ordinary crash shape rather than a defect. The lifecycle fold only demands a `tool/call` pairing when its step closes (`assertNoUnresolvedTools(toolLifecycles, "step/end")`), so a call whose step is still open at the end of the log is exactly what the engine's own `interruptedTurnClosers()` is about to close on resume. Found by pointing the tool at a real store rather than at a fixture: a 2970-event v4 session carrying an unresolved call in its open tail was reported as `dangling-tool-call` while the verifier shipped in the desktop's `0.2.0-rc.2` bundle accepts it. The detector now tracks step boundaries, reports a call only when its step closed without a result (or the id is empty, which the fold refuses on the call itself), and leaves the open tail to the `open-tail` flag.
- **An idle tool-result prune pass no longer leaves a session unloadable** ([#8812](https://github.com/deepseek-ai/deepseek-harness/discussions/8812)). The pruner rewrites old results while no turn is open — `compaction/prune` rows followed by replacement `tool/result` rows whose `surfaceOp` is a replace range — and both released readers route every non-append `tool/result` through a turn requirement (`requireTurn()` in `assertReleasedV4Relationships`, `else if (openTurn === null) throw "tool/result replacement is outside an open turn"` in the 0.2.0-rc.2 worker). After `turn/end` there is no open turn, so the writer emits a log its own reader refuses and the whole session stops loading, with no in-product recovery. New health code `prune-tail-outside-turn`; the repair cuts the log back to the `turn/end` the pass followed, and it only does so when **everything** after that boundary is the prune pass itself. That is what makes this one repairable where a turn that simply kept writing past its `turn/end` ([#7824](https://github.com/deepseek-ai/deepseek-harness/discussions/7824)) is not: a prune replacement is pure surface metadata — the fold itself requires `sourceEventSeqs` to name exactly the surface nodes it shadows, all of which are still in the log — so the pre-prune surface comes back with no message, turn or tool result lost, while real work in the same position would be. A tail that carries anything else (a `user/message`, a new turn, a plugin event), a replacement that shadows a node at or after the cut, or a pass with no `turn/end` before it is refused with the reason spelled out, because dropping it would trade one unloadable log for another. Verified end to end against the verifier shipped in the desktop's own `0.2.0-rc.2` bundle (`worker.cjs`, which runs the relationship fold, `Session.fromRestore` and the content/stream cross-check): the pruner's exact output is refused with `tool/result is outside an open turn`, and the repaired artifact verifies. If the transcript still shows the pruned text after a repair, delete that session's projection cache (`<home>/storages/session_projcache*/sessions/<id>.json`) and let it rebuild.

### Fixed

- **The panel's own buttons work on DSH 0.2.0 again**: 「返回会话」 and 「⋯ → 用会话医生查看」 did nothing on the desktop, and the switch was skipped without a word. Cordis 4's context proxy throws `cannot get property "layout" without inject` for a direct read of a service the plugin did not declare, and the layout service is installed with `ctx.reflect.provide`, which puts no accessor on the context. The browser half declared only `sessions` and `locale`, so `ctx.layout` threw, the `ctx.get("layout")` sitting behind it was never reached, and `layoutOf()` returned `undefined` from its own `catch`. Every optional service read now goes through one `serviceOf(ctx, name)` helper that asks `ctx.get()` first — cordis' own optional lookup, which resolves a service whether or not it was declared — and only then falls back to a direct read, so a shell that declares no slot seats still reaches the overlay path instead of parking. Reproduced against the shipped framework rather than argued: with cordis 4.0.4 taken out of the app bundle and a provider registered, `ctx.layout` throws while `ctx.get("layout")` returns the service. `test/ui.test.mjs` now hands the plugin a context that mirrors that proxy (direct read throws, `get()` resolves); the button test fails against the previously shipped `plugin/client.js` and passes here. Reported with a fix by @Renzishi ([#6](https://github.com/xiaoshenming/dsh-session-surgeon/pull/6)).
- **The `duplicate-tool-call-id` repair no longer writes a file the loader refuses** ([#5909](https://github.com/deepseek-ai/deepseek-harness/discussions/5909)). Suffixing a later duplicate and remapping only `tool/result.source.callId` left `message.toolCallId` pointing at the old id, and the released lifecycle fold reads *that* member — so a repaired v4 log died on the next load with `format v4 tool/result at seq <n> requires toolCallId matching its tool source`. Rows now carry both members, and the mapping survives a `tool/result` surface replacement by remembering what the replaced row was given instead of counting the replacement as a fresh result (`tool/result surface replacement may change only content`). The embedded `data.stream` is rewritten with it: the verifier reassembles the stream and compares it against `message.content`, so ids that agree in one place and not the other are refused as `content disagrees with its embedded stream`. All three record shapes that carry the id are covered — the compact `tool-call-chunks` run, a `block-end` whose block the assembler returns verbatim, and an unmerged `tool-call-delta` the accumulator keeps when a name is empty — while a record whose id cannot be mapped makes the repair refuse rather than guess. Verified through the official generation verifier (`worker.cjs`, shipped in both 0.1.7-rc.2 and the desktop's 0.2.0-rc.2, which runs the relationship fold, `Session.fromRestore` *and* the stream cross-check): the raw duplicates are refused with `assistant/message repeats advertised tool call call_x`, the repaired artifact verifies, and dropping either the `toolCallId` or the stream rewrite makes that same artifact fail again. The check now runs in `test/duplicates.test.mjs` wherever the verifier is installed. Fix started by @Renzishi ([#6](https://github.com/xiaoshenming/dsh-session-surgeon/pull/6)).

## 0.2.1

> The rolling `#main` install reports **0.2.1** from 2026-09-29; this section is what that install carries.

### Fixed

- **A settlement-broken assistant row is now repaired, not just reported** — and this corrects what the entry below claimed in the previous release. `stream: []` was said to be unrepairable; measured against the installed runtime, it is not. `assertCurrentAssistantStreams` (persistence-jsonl `lib/index.js:1833`) expands the stream and then `continue`s **before** comparing `message.content`, `usage` and `message.source.replayState` whenever the expansion is empty, so an empty array is admissible at both gates — while a deleted or `null` stream is refused by the settlement gate *and* makes the expander throw `stream is not iterable`. The streamed blocks behind `stream` are already gone (that is the defect), so nothing recoverable is discarded: the conversation text lives in `message.content` and is never touched, and neither are `usage` or the replay state. `turn`/`step` are a different case and are not a guess at all — the log states which turn and step are open at that seq, which is exactly the value the row belongs to, and the repair writes that pair; when nothing is open at the seq (the row sits outside any turn) the member is left alone and reported as `settlement-unresolved` instead of invented. Verified end to end against the released gate rather than argued: seven broken shapes (stream deleted / `null` / a string, turn deleted / `-0` / a float, and both at once) each fail `Session.fromRestore` before the repair and construct after it, and a repaired real v4 log constructs while its 579 other assistant rows still pass their content cross-check unchanged. `-0` was mutated on a healthy row and the repair restored exactly the value the row originally carried, which is the correctness signal that the derivation recovers the true value rather than merely an admissible one.

### Added

- The panel is a **native center-column page** now, not a full-screen DOM takeover: the browser half registers its own row in the shell's sidebar panel list (`sidebar.panellist`) and its page in the layout's keyed `main` seat, both through `ctx.slots.inject`, so the shell owns the row box, the label, the active highlight and the collapsed rail exactly as it does for the shipped Plugins and Schedule pages. The row carries a real 16px stroke glyph (a speech bubble with a medical cross, `data-dsh-panel-entry="session-surgeon"`) instead of a `✚` text node, and sits at order `-10` — ahead of Plugins (0), Schedule (10) and the task board (20), where the injected row used to be. The ⋯ menu's 「用会话医生查看」 switches the shell to the page with `ctx.layout.selectPanel("session-surgeon")` and opens the picked session there; the page header's 「返回会话」 goes back to the conversation with `selectPanel(null)`. Every color, radius and border rides the shell's own tokens (`--dsw-alias-bg-base`, `--dsw-alias-interactive-bg-hover`, `--dsw-alias-border-l3`, `--dsw-radius-md`, `--dsw-alias-state-error-primary`…), so the page follows the active theme, skin and light/dark mode; `plugin/ui.css` carries no hard-coded color any more. Scanning, the root picker, the transcript, repair preview/apply and export are unchanged, and one shared body renders both mounts, so switching panels neither rescans the disk nor drops the open conversation. A shell that declares no slot seats (pre-0.1.7 web hosts) keeps the previous overlay and DOM-injected sidebar button, and `test/ui.test.mjs` asserts the registration, the fallback and the token-only stylesheet.
- `descriptor-catalog-fact`: a `subagent/descriptor` row the **v3→v4 child-catalog path** cannot turn into a supported catalog fact ([#7995](https://github.com/deepseek-ai/deepseek-harness/discussions/7995)). `historicalChildCatalogSource` → `childCatalogFact` is the only reader of `mode`, and it refuses a `provider` that is not a string, a `mode` outside `continuable`/`one-shot` when `version` is not 1, and — via `catalogFact` (`:927`) — a **missing `label` whenever the effective mode is `continuable`**, which includes every version 1 row, because version 1 is normalised to `continuable` before validation. The predicate is not read off the source: it is a 12-shape matrix asserted against the released function itself, so the check and the gate are the same statement. `mode` is a real property and `label` is free text, so neither can be invented — report-only. Two honest limits: the check runs on v1–v3 only (a stored v4 log no longer runs that migration), and only for an **unseeded** subagent child, because the catalog counts rows at `seq >= inheritedEventCount` and that cut is runtime state no on-disk header carries (`assertReleasedV4Header`'s allowed set is version/id/createdAt/isSeeded/delegationDepth/cwd/parentSession/origin/agentPreset). One direction *is* pinned by `assertReleasedV2Artifact`: `if (!header.isSeeded && cut !== 0) throw`, so an unseeded child provably counts the whole file. A seeded child is skipped rather than guessed at.
- `invalid-settlement-fields`: an `assistant/message` or `assistant/attempt` row whose `turn`/`step` is not a non-negative safe integer (`-0` counts as invalid) or whose `stream` is not an array. The seed/restore gate (`assertAssistantSettlementShape` in `dsh-session`, which the stored-log read path reaches through `Session.fromRestore`) refuses the **whole session** over one such row — `seed assistant/message at index 4002 has invalid settlement fields` — and until now we printed `health: ok` for it, another false negative in the one job this tool has. Reproduced against the installed runtime rather than read: a real v4 log constructs a `Session` untouched, and deleting `stream` — or setting it to `null`, or `turn` to `-0` — makes the same construction throw exactly that message. The writer's append path does not check these three fields, so a row can be written that only fails on the next load, and by then the log is the only witness. `stream` carries the streamed blocks (a non-empty array, 5..26 entries, in every healthy row measured). Checked from v1 up: a released v0 `assistant/message` may not carry `stream` at all (the v0→v1 payload gate rejects it as an unexpected member), so v0 stays with `v0-missing-member`. Measured at 0 hits across the 7 real logs on hand (v3 + v4) and ~1.6ms on a 140k-event log. **Superseded by `### Fixed` above: this was first shipped report-only on the belief that the row could not be made admissible, which the measurement disproved.**
- `v0-missing-member`: rows that kept their type but lost a member the **released v0 inventory requires** — `turn/end` without `reason`, `assistant/message` without `turn`/`step`/`message`/`message.content`, `user/message` without `id`/`role`/`content`/`source`, `tool/call` without `arguments`, `tool/result` without a message, `permission/preset` without `preset`, `agent/inbox/spliced` without `target`/`start`/`inserted`, `goal/change` without `kind`/`version`/`operation`, and a row with no `data` at all. The v0→v1 payload gate refuses the **whole session** over one such row (`… lacks required member "reason"`), and until now we printed `health: ok` for it — a false negative in the one job this tool has. The required sets are derived by **ablation against the released validator**: remove a member, keep it only when the gate refuses that removal, so every entry is enforced by the code that will judge the file. The released package also *declares* its inventory (`RELEASED_V0_EVENT_DISPOSITIONS`, 51 types) and the gate enforces it generically; every entry here matches that declaration, but the declaration is not a safe substitute — it requires `chunk` on `assistant/chunk` while the gate accepts a chunk row that is missing `chunk` *and* one carrying an unexpected extra member, i.e. that type is never validated on this path. Coverage therefore stays partial on purpose, per-block members are skipped (they vary by block type), and the check runs only on a v0 artifact, where that gate actually runs. Report-only: the member is not recoverable from the artifact. Measured at 0 hits across 12 logs, including a recorded v0 fixture that stays `ok`, and the new detector costs ~5ms on a 140k-event log.
- Inspect reports **steps that continue a turn the log already closed** (#7824), and a `turn/end` that lands while a step is still open. The released relationship walker refuses the whole session for the first shape: the v1→v2 stage re-runs v0-to-v1's `assertReleasedArtifactRelationships` over the artifact it just produced, so a log whose turn closed before its steps finished dies with `assistant/message does not match an open turn and step` (`step/start … does not match the open turn and next step` for the step-opening variant), wrapped by the orchestrator as *refuses the transformed artifact*. The sibling shape is `turn/end <n> crosses an open step` — the writer states the same rule in `dsh-session/lib/invariant.js`. New health codes `step-after-turn-end` and `turn-end-while-step-open`, both **report-only**: merging the split turn and splitting it in two have no unique answer inside the artifact, and splitting would renumber every later seq and every declared range. Reproduced against the released stage (`restoreReleasedV2Artifact`: a healthy control is accepted, a premature `turn/end` followed by `assistant/message` is refused with the reporter's exact string) and measured at zero hits across the six local sessions. Detection is deliberately narrow — it only fires when a step-scoped event carries a `turn` that already ended, so minimal logs that omit `step/start` stay quiet.
- Generation check against **0.1.7-rc.1** (format **v4**, npm `next` at the time; `latest` was 0.1.5-rc.3 and moved to 0.1.7-rc.2 on 2026-09-27): a v3/v4 `session.vN.jsonl.zstd` is decoded, inspected and repaired by the same paths as v0 (`health` stays `ok` on healthy files, a seq gap in a v4 log is still dropped, and the header generation/`isSeeded` survive the rewrite). Nothing in the repair contract was version-gated on v0 beyond the `MIGRATES_V0_ON_LOAD` switches that already follow the installed runtime.
- 0.1.5-rc.1 converter refusals on released v0 sessions (`v0-preset-extra-member` [#6189](https://github.com/deepseek-ai/deepseek-harness/discussions/6189), `v0-descriptor-version` / plugin source kinds [#6151](https://github.com/deepseek-ai/deepseek-harness/discussions/6151), `v0-plugin-source-form` [#6194](https://github.com/deepseek-ai/deepseek-harness/discussions/6194), `v0-chunk-provenance` [#6175](https://github.com/deepseek-ai/deepseek-harness/discussions/6175)). The frozen released-v0 inventory refuses shapes earlier writers emitted, so sessions become unopenable after upgrading. Repair (only when the installed runtime migrates v0, i.e. format ≥ 1) keeps just `preset` on `permission/preset`, sets `subagent/descriptor` version 3, aligns plugin-source `form` with `summary`/`sections`, and cites the on-disk chunk run for `assistant/message`. Verified against the real 0.1.5-rc.1 `sessionFormatV0ToV1` stage: refused before, clean migration after. Unknown event types (`session/imported`, plugin messages) are still inspect-only — the converter refuses those even when `ignorable`, and repair does not delete events.
- Two more released-writer refusals from the [#6559](https://github.com/deepseek-ai/deepseek-harness/discussions/6559) inventory, still present on 0.1.7-rc.1: `v0-retired-source-kind` — a message `source.kind` literal the writer retired (`instruction-hint`) is no longer in the v2→v3 `SOURCE_KINDS`, so `assertSource` refuses the session as unclassified; the member set is identical to the current `plugin` source, so repair renames the kind only. `v0-inbox-inserted-message` — `agent/inbox/spliced` inserted messages that lack `id`/`role`, which the v0→v1 `messageValue` inventory refuses; repair fills the missing id and the `"user"` role the validator itself passes in. Sources carrying members beyond the released plugin set are left untouched (report only). ### Not in scope (still refuse / warn only)

- `v4-literal-plugin-source`: a log already at **v4** whose message source still carries the retired `{kind:"plugin", plugin}` wrapper is refused by the official reader on the ordinary read path (`format v4 message requires a producer-owned source kind` — measured on 0.1.7-rc.1: the same row with `kind:"plugin:dsh-mnemon"` reads cleanly). v4 wants the producer's own kind, which the v3→v4 stage derives from the package name; for an unknown plugin there is no single answer, so inspect reports the rows and repair does not touch them ([#7772](https://github.com/deepseek-ai/deepseek-harness/discussions/7772)). Below v4 the wrapper is legal and the stage lifts it, so the report is gated on this file's own header generation.

- Empty `callId` / empty `tool_calls[].id` / dangling `tool/call`: inspect warns (`empty-tool-call-id` / `dangling-tool-call`), repair does not invent a `tool/result` or callId.
- Unknown plugin event types: report `unknown-type`, do not stamp `ignorable`.
- Web Chat `received more than one start Match`: frontend fold, not a disk defect.
- Arbitrary dual-write branch picking when the packed/live-writer signatures do not match.
